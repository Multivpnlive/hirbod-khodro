# Hirbod Khodro Installer

## نصب با یک دستور

روی سرور Ubuntu با دسترسی root اجرا کنید:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Multivpnlive/hirbod-khodro/main/installer/install-from-github.sh)
```

اسکریپت آخرین نسخه منتشرشده را دریافت می‌کند، دامنه را می‌پرسد و نصب را انجام می‌دهد. نیازی به ورود به پوشه پروژه یا دریافت دستی مخزن نیست.

## بروزرسانی با یک دستور

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Multivpnlive/hirbod-khodro/main/installer/update-from-github.sh)
```

دامنه از تنظیمات Caddy تشخیص داده می‌شود؛ در صورت عدم تشخیص، از کاربر پرسیده می‌شود.

حالت پیش‌فرض، پیش‌بررسی بدون اعمال تغییرات است. برای بروزرسانی واقعی، گزینه ۲ را انتخاب و عبارت UPDATE را وارد کنید.

در بروزرسانی واقعی، اسکریپت تفاوت مهاجرت‌های دیتابیس را بررسی می‌کند، پیش از اجرای مهاجرت‌های جدید یک نسخهٔ پشتیبان PostgreSQL با دسترسی محدود کنار نسخهٔ برنامه ذخیره و صحت آن را بررسی می‌کند، سپس مهاجرت‌ها را به ترتیب اجرا می‌کند. اگر تهیه یا بررسی پشتیبان یا هر مهاجرتی شکست بخورد، جایگزینی برنامه انجام نمی‌شود و مسیر پشتیبان در پیام خطا اعلام می‌شود. پیش‌بررسی هیچ تغییری در برنامه یا دیتابیس ایجاد نمی‌کند.

## دستورات اختیاری

```bash
# پیش‌بررسی
bash installer/update-from-github.sh --domain app.example.com --dry-run

# بروزرسانی واقعی؛ پس از بررسی و تهیه پشتیبان
bash installer/update-from-github.sh --domain app.example.com --yes

# پیش‌بررسی نصب تازه
bash installer/preflight.sh --domain app.example.com
```

## راه‌اندازی ایمیل تأیید حساب و بازیابی رمز عبور؛ راهنمای صفر تا صد

این راهنما ارسال ایمیل‌های تأیید حساب و بازیابی رمز عبور را برای هر نصب مستقل با سرویس Resend، از ساخت حساب تا آزمایش نهایی توضیح می‌دهد. هر نصب از دامنهٔ ارسال، رکوردهای DNS، فرستنده و API Key متعلق به خودش استفاده می‌کند؛ دامنه‌ای به‌صورت مشترک برای همهٔ سرورها تعیین نشده است. این راه‌اندازی فقط برای ارسال ایمیل است و صندوق ورودی برای دریافت پاسخ ایجاد نمی‌کند.

### سایت‌هایی که لازم دارید

1. [ساخت حساب یا ورود به Resend](https://resend.com/signup)؛ این سرویس ایمیل را ارسال می‌کند.
2. پنل DNS دامنهٔ خودتان؛ همان سایتی که رکوردهای دامنه در آن مدیریت می‌شوند. اگر DNS دامنه در Cloudflare است، از [پنل Cloudflare](https://dash.cloudflare.com/) استفاده کنید؛ در غیر این صورت وارد پنل شرکت میزبانی DNS یا ثبت‌کنندهٔ دامنه شوید.
3. نشانی HTTPS سامانه‌ای که روی همین سرور نصب کرده‌اید؛ آن را با دامنهٔ اختصاصی همان نصب باز کنید تا بازیابی رمز عبور را آزمایش کنید.

برای DNS باید دسترسی مدیریتی دامنه‌ای را داشته باشید که برای همین نصب انتخاب کرده‌اید. اگر نمی‌دانید DNS آن دامنه در کدام پنل است، نام‌سرورها را در پنل ثبت‌کننده بررسی کنید و رکوردها را در پنلی وارد کنید که آن نام‌سرورها به آن اشاره می‌کنند.

### مرحلهٔ ۱: افزودن دامنهٔ ارسال در Resend

1. وارد [Resend](https://resend.com/signup) شوید و حساب خود را بسازید یا وارد حساب شوید.
2. از داشبورد Resend بخش **Domains** را باز و **Add Domain** را انتخاب کنید.
3. دامنهٔ ارسال متعلق به همین نصب را وارد کنید؛ برای نمونه می‌توانید یک زیردامنه مانند `mail.your-domain.tld` انتخاب کنید. نشانی فرستنده‌ای که در اسکریپت وارد می‌کنید باید از دامنه‌ای باشد که اینجا تأیید می‌کنید.
4. نزدیک‌ترین منطقهٔ موجود به بیشتر دریافت‌کنندگان ایمیل را انتخاب کنید.
5. دامنه را اضافه کنید. در صفحهٔ آن، بخش **DNS Records** یا **Records** را باز نگه دارید؛ Resend رکوردهای اختصاصی دامنهٔ شما را نمایش می‌دهد.

Resend ارسال از دامنهٔ تأییدنشده را نمی‌پذیرد و استفاده از زیردامنه را برای جدا نگه‌داشتن اعتبار ارسال ایمیل پیشنهاد می‌کند. اگر می‌خواهید از نشانی دیگری استفاده کنید، همان دامنه باید در Resend تأیید شود و هنگام نصب نیز فرستنده‌ای از همان دامنه وارد کنید.

### مرحلهٔ ۲: ثبت رکوردهای DNS

1. در پنل DNS، ناحیهٔ دامنهٔ انتخاب‌شده برای همین نصب را باز کنید. اگر DNS شما در Cloudflare است، مسیر معمول **Websites → دامنهٔ خودتان → DNS → Records** است.
2. برای هر رکوردی که Resend نشان می‌دهد، یک رکورد جدید با همان **Type**، **Name/Host**، **Value/Target** و در صورت نمایش **Priority** بسازید. مقدارها را دقیقاً Copy/Paste کنید؛ این مقدارها برای حساب و دامنهٔ شما ساخته شده‌اند.
3. اگر پنل DNS خودش نام دامنه را به انتهای **Name/Host** اضافه می‌کند، قالب ورودی همان پنل را رعایت کنید تا نام دامنه دوبار تکرار نشود.
4. رکوردهای CNAME موردنیاز Resend را در Cloudflare روی **DNS only** بگذارید؛ ابر نارنجی یا Proxy برای این رکوردها باید خاموش باشد.
5. فقط رکوردهایی را اضافه یا اصلاح کنید که Resend برای دامنهٔ ارسال همین نصب اعلام کرده است. رکوردهای وب‌سایت، MX ایمیل‌های فعلی یا رکوردهای مربوط به نصب‌های دیگر را حذف یا جایگزین نکنید.
6. به Resend برگردید و صفحهٔ دامنه را بازخوانی کنید. وضعیت باید به **Verified** تغییر کند. معمولاً چند دقیقه زمان می‌برد، اما انتشار DNS ممکن است تا ۷۲ ساعت طول بکشد.

اگر هنوز تأیید نشده است، نام و مقدار هر رکورد را با پنل DNS تطبیق دهید، Proxy رکوردهای CNAME را خاموش کنید و کمی بعد دوباره بررسی کنید. راهنمای رسمی Resend دربارهٔ [افزودن و تأیید دامنه](https://resend.com/docs/add-a-domain) را ببینید.

### مرحلهٔ ۳: ساخت کلید محدود برای ارسال

1. در Resend بخش **API Keys** را باز و **Create API Key** را انتخاب کنید.
2. نامی قابل‌شناسایی مانند `hirbod-production-mailer` بگذارید.
3. دسترسی **Sending access** را انتخاب کنید و اگر امکان محدودکردن دامنه نمایش داده شد، کلید را فقط به دامنهٔ ارسال تأییدشدهٔ همین نصب محدود کنید.
4. کلید را بسازید و همان لحظه آن را کپی کنید؛ Resend مقدار کامل کلید را معمولاً فقط هنگام ساخت نشان می‌دهد. کلید باید با `re_` شروع شود.
5. کلید را در چت، ایمیل، فایل Git، تصویر صفحه یا دستور خط فرمان قرار ندهید. آن را فقط در ورودی مخفی اسکریپت روی سرور وارد کنید.

Resend برای API Key دسترسی ارسال و محدودکردن کلید به دامنه را پشتیبانی می‌کند؛ این کار دسترسی کلید برنامه را به حد لازم کاهش می‌دهد. جزئیات در [راهنمای API Keys](https://resend.com/docs/dashboard/api-keys/introduction) آمده است.

### مرحلهٔ ۴: اجرای نصب ایمیل روی سرور همین نصب

این مرحله را از نشست SSH همان سروری اجرا کنید که برنامه و Supabase آن نصب هستند. با دسترسی `root` اجرا کنید:

```bash
cd /opt/hirbod/app
bash installer/setup-email.sh
```

اسکریپت از شما این موارد را می‌پرسد:

- **Resend API key**: کلید مرحلهٔ قبل را Paste کنید. هنگام تایپ یا Paste، حروف روی صفحه نمایش داده نمی‌شوند؛ این طبیعی است. سپس Enter بزنید.
- **Sender identity**: نشانی فرستنده‌ای وارد کنید که دامنه‌اش در مرحلهٔ اول برای همین نصب تأیید شده است؛ برای نمونه `Hirbod Khodro <no-reply@your-domain.tld>`. اگر این اسکریپت قبلاً روی همین سرور اجرا شده باشد، Enter مقدار فعلی را نگه می‌دارد؛ فقط وقتی آن را نگه دارید که متعلق به دامنهٔ اختصاصی همین نصب باشد، وگرنه نشانی جدید را وارد کنید.

اسکریپت کلید را در فایل محافظت‌شدهٔ سرور ذخیره می‌کند، secret امضای ارتباط Supabase را در صورت نیاز می‌سازد، سرویس ایمیل و تنظیمات Auth را نصب می‌کند، Gateway واقعی Docker را پس از راه‌اندازی Auth تشخیص می‌دهد و اتصال را بررسی می‌کند. پیش از تغییر، از فایل‌های قبلی و روشن/خاموش بودن سرویس snapshot می‌گیرد و اگر نصب شکست بخورد، تنظیمات و وضعیت سرویس قبلی را برمی‌گرداند.

برای این کار لازم نیست فایل‌های `.env` یا `docker-compose.yml` را دستی ویرایش کنید. اگر اسکریپت خطا داد، همان پیام خطا را بررسی کنید؛ کلید Resend را در گزارش یا پیام برای دیگران قرار ندهید.

اگر برنامه از قبل روی سرور نصب است و فقط می‌خواهید سلامت پیکربندی را بدون تغییر بررسی کنید، این دستور را اجرا کنید:

```bash
cd /opt/hirbod/app
bash installer/setup-email.sh --check
```

### مرحلهٔ ۵: آزمایش بازیابی رمز عبور

1. در مرورگر آدرس سامانهٔ همین نصب را باز کنید؛ برای نمونه `https://YOUR_APP_DOMAIN` را با دامنهٔ واقعی این سرور جایگزین کنید.
2. در صفحهٔ ورود، گزینهٔ **فراموشی رمز عبور** را بزنید.
3. نشانی ایمیل یک حساب آزمایشی موجود و تحت کنترل خودتان را وارد کنید.
4. صندوق ورودی و پوشهٔ Spam/Junk را بررسی کنید. فرستنده باید نشانی تنظیم‌شده در مرحلهٔ قبل باشد.
5. پیوند داخل ایمیل را باز کنید، رمز تازه‌ای تعیین کنید و با همان رمز وارد شوید.
6. در داشبورد Resend بخش **Emails** را باز کنید و وضعیت همان پیام را ببینید.

فراموشی رمز را برای ایمیل واقعی شخص دیگری آزمایش نکنید. بررسی `--check` فقط سلامت سرویس و دسترسی Supabase Auth به آن را تأیید می‌کند؛ دریافت واقعی ایمیل را باید با حساب آزمایشی خودتان بررسی کنید.

### بررسی وضعیت و رفع اشکال

```bash
systemctl status hirbod-mailer.service --no-pager
journalctl -u hirbod-mailer.service --since '15 minutes ago' --no-pager
docker compose -f /opt/hirbod/supabase-project/docker-compose.yml logs --tail=80 auth
```

- اگر اسکریپت می‌گوید API Key تنظیم نشده، مطمئن شوید کلید کامل Resend را در ورودی مخفی وارد کرده‌اید و با `re_` شروع می‌شود.
- اگر Resend دامنه را تأیید نمی‌کند، Type/Name/Value را دقیق تطبیق دهید، Proxy رکوردهای CNAME را خاموش کنید و برای انتشار DNS زمان بدهید.
- اگر Resend پیام را رد می‌کند، تأییدشدن دامنه و هم‌خوانی دامنهٔ فرستنده با کلید محدودشده را بررسی کنید.
- اگر پیام در Resend **Delivered** است ولی در Inbox نیست، Spam/Junk و فیلترهای گیرنده را بررسی کنید.
- اگر Supabase Auth به سرویس دسترسی ندارد، خروجی `--check` و وضعیت Auth را بررسی کنید. تنظیم Gateway و راه‌اندازی مجدد Auth را اسکریپت انجام می‌دهد.

در صورت درخواست کمک، خروجی خطا را پس از حذف یا پوشاندن API Key، secretها و نشانی‌های خصوصی ارسال کنید.

### نکات امنیتی و پشتیبان‌گیری

- فایل کلیدها فقط روی سرور نگهداری می‌شود؛ آن را در Git، اسکرین‌شات یا پیام قرار ندهید.
- فایل‌های snapshot و پشتیبان حاوی تنظیمات محرمانهٔ ایمیل هستند. دسترسی آن‌ها را محدود و نسخه‌های پشتیبان را در محل امن نگهداری کنید.
- قالب بکاپ نسخهٔ ۳، مقدار `format_version: 3` و `encrypted: false` را تغییر نمی‌دهیم. فایل‌های محرمانهٔ ایمیل در این قالب رمزگذاری نمی‌شوند؛ بنابراین فایل بکاپ را محرمانه تلقی کنید.
- بکاپ قدیمی که هیچ‌یک از سه فایل ایمیل را ندارد همچنان معتبر است؛ اما در بکاپ جدید وجود فایل‌های ایمیل همه‌یا‌هیچ بررسی می‌شود.
- Resend در این راه‌اندازی فقط ارسال انجام می‌دهد. نشانی `no-reply@...` صندوق ورودی یا امکان دریافت پاسخ ایجاد نمی‌کند.

## بررسی‌های نصب

- Ubuntu 22.04 یا 24.04 و معماری x86_64
- منابع CPU، حافظه و فضای دیسک
- DNS دامنه و دسترسی شبکه
- پورت‌های موردنیاز برنامه و Supabase
- جلوگیری از بازنویسی نصب موجود

## الزامات امنیتی و نگهداری

- تنظیمات و داده‌های Supabase موجود باید حفظ شوند.
- فایل‌های محرمانه و `.env` واقعی نباید وارد Git شوند.
- کلیدها و گذرواژه‌ها فقط روی سرور نگهداری شوند.
- مهاجرت‌های پایگاه داده نباید بدون دستورالعمل همان نسخه اجرا شوند.
- پیش از هر بروزرسانی واقعی، نسخه پشتیبان معتبر تهیه شود.
- کنترل دسترسی مدیر و مجوزهای بازیابی حفظ شوند.
- سرویس با حداقل سطح دسترسی لازم اجرا شود.
- HTTPS و سلامت سرویس پس از نصب بررسی شوند.

## مهاجرت پایگاه داده

اسکریپت بروزرسانی، مهاجرت‌های پایگاه داده را خودکار اجرا نمی‌کند. مهاجرت‌ها فقط طبق دستورالعمل نسخه مقصد و پس از تهیه پشتیبان انجام شوند. از اجرای تکراری مهاجرت‌ها خودداری کنید.
